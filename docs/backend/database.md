# Database Guide

## Overview

Framehouse Hub uses PostgreSQL via the `@payloadcms/db-postgres` adapter with **`push: false`** — schema changes must go through the migration system, never auto-synced. Locally the database runs in Docker; in cloud it is Neon (serverless Postgres).

---

## Local vs Cloud Setup

### Local (Docker)

`docker-compose.yml` spins a Postgres container on port `5432`. The `DATABASE_URI` in `.env.local` points at it:

```
DATABASE_URI=postgresql://postgres:postgres@localhost:5432/framehouse
```

Use `scripts/verify-local.sh` to spin an ephemeral Postgres on `:5433` for blank-slate validation (see below).

### Cloud (Neon)

Neon connection strings are detected automatically by the adapter, which lowers the pool to 4 connections to stay within serverless limits. The secret is stored in Secret Manager as `DATABASE_URI_DEV` and mounted on both Cloud Run services.

## Migration Workflow

> Never use `push: true`. The adapter config explicitly sets `push: false`. Auto-push silently drops or alters columns and creates drift that CI will catch as a failure.

### Step-by-step

1. **Make schema changes** in the relevant collection config under `src/collections/` or `src/globals/`.

2. **Regenerate types** — after any field or collection change:
   ```bash
   pnpm generate:types
   ```
   This regenerates `src/payload-types.ts`. Commit this file alongside the migration.

3. **Generate the migration** — Payload diffs your config against the current DB state and emits SQL:
   ```bash
   pnpm payload migrate:create
   ```
   This produces two files in `src/migrations/`:
   - `<timestamp>_<name>.ts` — the executable migration (TypeScript, uses `sql` tagged template)
   - `<timestamp>_<name>.json` — Payload's internal schema snapshot

4. **Review both files** before committing. Verify the SQL is what you intended — check for unexpected `DROP` statements or column renames.

5. **Commit both files** together with the config changes and the updated `src/payload-types.ts`.

6. **Apply locally**:
   ```bash
   pnpm payload migrate
   ```

### CI drift check

CI runs this after applying all migrations:

```bash
pnpm payload migrate:create --name check_drift
```

If the working tree is dirty after this command (i.e., a new migration file was generated), the `pr-validation.yml` job fails. This enforces that committed migrations fully describe the current config — no undeclared schema changes can sneak in.

## Inspecting Generated Migrations

Migrations live in `src/migrations/`. Each `.ts` file exports `up` and `down` functions using `@payloadcms/db-postgres`'s `sql` tagged template. The `.json` file is Payload's internal snapshot — do not hand-edit it.

```bash
# List all migrations in order
ls src/migrations/*.ts | grep -v index.ts

# The index file registers all migrations with the adapter
cat src/migrations/index.ts
```

The `index.ts` file is auto-generated by `migrate:create` — do not manually edit it.

## Connection String Formats

| Environment | Format |
|-------------|--------|
| Local Docker | `postgresql://postgres:postgres@localhost:5432/framehouse` |
| Local ephemeral (verify-local.sh) | `postgresql://postgres:postgres@localhost:5433/framehouse_test` |
| Neon (cloud) | `postgresql://<user>:<pass>@<host>.neon.tech/<db>?sslmode=require` |

Neon strings are auto-detected by the adapter (hostname contains `neon.tech`), which triggers the reduced pool size.

## Key Database Indices

| Index | Type | Table | Purpose |
|-------|------|-------|---------|
| `media_full_search_idx` | GIN full-text | `media` | Powers `/api/media/search` — covers `title`, `filename`, `original_filename`, `technical_camera_model`, `technical_lens_model`, `shoot_name`, `location_address` |
| `media_accession_id_idx` | UNIQUE btree | `media` | Enforces uniqueness of archival accession IDs |
| `media_capture_date_idx` | btree | `media` | Sorts/filters by capture date |
| `idx_portfolios_blocks_grid_unique_anchor` | UNIQUE partial | `portfolios_blocks_grid` | Prevents duplicate section anchors within a portfolio |
| `idx_portfolios_blocks_grid_parent_layout` | partial | `portfolios_blocks_grid` | Composite filter on `(_parent_id, layout_style)` for analytics |
| `idx_portfolios_blocks_grid_section_name` | partial | `portfolios_blocks_grid` | Admin support queries across section names |
| `pricing_meta_image_idx` | btree | `pricing` | FK lookup on pricing global's meta image |

When adding new searchable fields to Media, update both:
- The migration that alters `media_full_search_idx` (drop and recreate — GIN indices cannot be altered in-place)
- The `/api/media/search` route handler

## FK Constraints Rule

For new Media-referencing foreign keys:

- Use `ON DELETE SET NULL` with a nullable column.
- Do **not** use `CASCADE` — it works at the SQL level but creates drift against Payload's auto-generated schema.

```sql
-- Correct pattern
ALTER TABLE some_table
  ADD COLUMN media_id integer REFERENCES media(id) ON DELETE SET NULL;
```

## Seeding

```bash
pnpm seed
```

Entry point: `src/seed/standalone.ts` → calls `seedHubContent` from `src/seed/index.ts`.

What it creates:
- System admin user: `sys.admin@framehouseworks.com` / `password123`
- Header and Footer globals
- Pricing global
- Sample Pages
- Sample Categories

Seeding always realigns the system admin account — it is idempotent for that user. It does **not** upload media bytes to GCS in cloud mode (workaround: upload manually via dashboard after seed).

## Blank-Slate Verification

```bash
# Spin ephemeral Postgres on :5433, migrate, seed, then tear down
./scripts/verify-local.sh

# Keep the DB running for manual inspection
./scripts/verify-local.sh --keep-open

# Tear down a --keep-open run
./scripts/cleanup-local.sh
```

This script is also executed by the **pre-push** Husky hook alongside `lint` and `build`. The same flow runs in CI against an ephemeral Neon branch (`pr-validation.yml`).

---

## Why `push: false`

`push: true` auto-applies schema changes to the live database on server start. In a team/CI environment this causes:

- Silent column drops if a field is removed from config
- Unreviewed schema changes reaching production
- Drift between what Payload thinks the schema is and what migrations describe

With `push: false`, every schema change is explicit, reviewable, reversible, and tracked in git.
