# Specification: FRH-72 — UUID Primary Key Migration

> **IMPLEMENTATION STATUS:** SPECCED — NOT STARTED

**Base Branch:** `dev`
**Date:** 2026-10-26

---

## 1. Core Objective & Scope

- **Objective:** Migrate every Payload CMS collection from auto-incrementing integer serial primary keys to native UUID v4 primary keys. This eliminates enumerable user/resource IDs (IDOR vector), aligns the DB schema with the storage-path contract that already uses UUID segments for `assetId`, and removes the brittle `Number()` / `String()` coercion layer scattered across API routes and dashboard pages. The application is pre-launch (`COMING_SOON=true`), so a single-phase destructive cutover is acceptable — no dual-write or background sync.
- **Ticket Reference:** FRH-72
- **In-Scope Files/Modules:**
  - `src/payload.config.ts` — add `idType: 'uuid'` to `postgresAdapter`
  - `src/migrations/` — new migration(s) generated by `pnpm payload migrate:create`
  - `src/app/api/**` — all custom API routes (signed-url, register-gcs, register-local, smart-collections, media/[id], media/search, media/reprocess, dashboard/reviews, admin/diagnostic-sessions, portfolio-review/*, users/me/*)
  - `src/app/(dashboard)/**` — all dashboard pages that cast `Number(id)` from route params
  - `src/app/(portfolio)/**` — public portfolio page preview/unlock token validation
  - `src/collections/*/` — hooks, access modules, endpoints that reference `user.id` or cast relation IDs to `number`
  - `src/access/` — `ownerOrAdmin.ts`, `adminOrSelf.ts` (no changes needed; `user.id` equality works for both int and UUID)
  - `src/lib/storage-paths.ts` — already uses `string` typing; no changes needed
  - `src/seed/` — seed script hardcoded integer relation values
  - `src/components/` — frontend components with `as { id: number }` type assertions
  - `scripts/worker/main.go` — already string-typed `UserID`; no changes needed
  - `src/payload-types.ts` — regenerated via `pnpm generate:types`
- **Explicit Non-Goals:**
  - Non-dashboard pages (marketing site, coming-soon, app route group)
  - Go worker code changes (already string-typed)
  - Storage path format changes (already UUID-based for `assetId` segment; `userId` is already `String()` cast)
  - Dual-write / incremental migration strategy
  - Any changes to the `COMING_SOON` middleware gate

## 2. Platform & Free-Tier Impact Check

| Area | Impact | Details |
|------|--------|---------|
| **Payload Schema** | Yes | `postgresAdapter({ idType: 'uuid' })` changes PK type for ALL collections + globals _rels tables |
| **Route Groups** | Yes | `(dashboard)` pages with `Number(id)` casts, `(portfolio)` preview token validation |
| **Migrations** | Yes | One destructive migration: drops integer PKs/FKs, adds UUID PKs/FKs across all tables |
| **Worker / GCP** | No | Go worker `parseStoragePathV2` already treats `UserID`/`AssetID` as `string` — no changes |
| **Access Control** | No | `ownerOrAdmin`, `adminOrSelf`, `creativeOrAdmin` use `user.id` via Payload `equals` — type-agnostic |
| **Storage Paths** | No | `buildStoragePath` already accepts `userId: string`; callers already do `String(user.id)` |
| **Free-Tier Risk** | No | UUID columns use 16 bytes vs 4 bytes for int; negligible at pre-launch scale. No new Cloud Run services. |

## 3. User Flows & Acceptance Criteria

- [ ] **AC-1:** Given a clean database, When `pnpm payload migrate` runs, Then all tables use `uuid` PKs and all FK/relationship columns reference UUIDs. `\d users` shows `id uuid NOT NULL DEFAULT gen_random_uuid()`.
- [ ] **AC-2:** Given a running dev server, When a creative uploads a file via signed-url then register-gcs, Then the Media doc is created with a UUID `id`, the `storagePath` contains the user's UUID in segment [1], and the `owner` field stores a UUID reference.
- [ ] **AC-3:** Given a running dev server, When a creative uploads a file via register-local, Then the same UUID behaviour as AC-2 applies to the local enclave path.
- [ ] **AC-4:** Given the dashboard, When a user navigates to `/dashboard/portfolios/{uuid}`, Then the page loads the correct portfolio without `NaN` errors.
- [ ] **AC-5:** Given the portfolio public page, When a preview token is validated, Then the HMAC validation works with UUID-based `portfolioId` string comparison (no `Number()` cast).
- [ ] **AC-6:** Given a smart-collection API call to `PATCH /api/smart-collections/{uuid}`, Then the owner guard resolves correctly against `user.id` (UUID string equality, no `Number()` cast).
- [ ] **AC-7:** Given `scripts/verify-local.sh`, When run after migration, Then zero schema drift is reported and seed data is created with UUID IDs.
- [ ] **AC-8:** Given `IS_BUILD_PHASE=true pnpm build`, Then the build passes with no type errors from the regenerated `payload-types.ts` (all `id` fields are `string`).

## 4. Adversarial Review & Self-Correction Log

| # | Category | Issue Found | Remediation |
|---|----------|-------------|-------------|
| 1 | **Type Coercion** | 19 instances of `Number(id)` / `Number(idStr)` in API routes and dashboard pages cast route params to integer before passing to `payload.findByID()`. With UUID PKs, `Number('550e8400-...')` produces `NaN`, breaking every dynamic route. | Phase 2 removes all `Number()` casts on document IDs. Route params are passed as-is (string). `isNaN()` guards are replaced with UUID format validation or removed entirely (Payload returns 404 for invalid IDs). |
| 2 | **Type Assertion** | 11 instances of `as { id: number }` across components and API routes hardcode the ID type to `number`. Post-migration these will be incorrect and mask type errors. | Phase 3 changes all `as { id: number }` to `as { id: string }` or uses the regenerated `payload-types.ts` type directly. |
| 3 | **Relation ID Coercion** | `register-gcs` and `register-local` both do `Number(sessionId)` and `Number(uploadBatchId)` when assigning relation values. Post-migration, relation IDs are UUID strings; `Number()` produces `NaN`. | Phase 2 removes `Number()` wrappers on relation ID assignments. Values passed through as strings. |
| 4 | **HMAC Token Validation** | `validatePreviewToken` and `validateUnlockCookie` in `(portfolio)/p/[slug]/page.tsx` encode `portfolioId` as `Number(idStr)`. With UUID PKs, the token format must switch to string-based ID comparison. The `idStr` is extracted from the HMAC payload and compared with `Number()` — this breaks. | Phase 3 changes token validation to use string comparison (`idStr !== String(portfolioId)`). Token generation in `portfolios.ts` actions must also be updated to emit string IDs. |
| 5 | **Seed Script Hardcoding** | The seed script (`src/seed/index.ts`) creates records with `payload.create()` calls that may return and cross-reference integer IDs. Post-migration, all returned `.id` values are UUIDs — any arithmetic or `Number()` operations on them will fail. | Phase 2 audits the seed script for any `Number()` coercion on returned IDs and ensures all cross-references use the returned string ID values directly. |
| 6 | **Smart-Collection Owner Guard** | `getAuthedOwner()` in `smart-collections/[id]/route.ts` does `ownerId !== user.id` — this already works for string equality. BUT the function signature is `async function getAuthedOwner(id: number)` — the type annotation is wrong post-migration. | Phase 2 changes the function signature to accept `string` instead of `number`. |
| 7 | **Portfolio Dashboard Redirect** | `EditPortfolioPage` does `Number(id)` then `isNaN(portfolioId)` as a guard. Post-migration every UUID will be `NaN`, causing all portfolio edit pages to 404. | Phase 3 removes the `Number()` cast and replaces the `isNaN` guard with a UUID format regex or removes it (Payload's findByID handles invalid IDs). |

## 6. Rollback Plan

- **Pre-launch context:** The application is behind `COMING_SOON=true`. There are no real users or production data to preserve.
- **Database rollback:** The migration is destructive (integer PKs to UUID PKs). Rollback = revert the `idType: 'uuid'` config change, delete the generated migration file(s), and re-run `scripts/reset.sh` to reset the local database to the previous schema + seed.
- **Code rollback:** `git revert` the merge commit on `dev`. All changes are additive code removals (removing `Number()` casts) — no new features introduced.
- **Production deployment:** Not applicable. The app is pre-launch. The cutover runs in a maintenance window against the Neon staging DB. If it fails, truncate all tables and re-seed.
